## 0. 先看结论

litrag 不是单纯的“论文问答工具”，也不是普通的“考研资讯网站”。

它最终要做的是：

> **面向本科生的升学变化雷达 + 带原文页码的文献证据工作台。**

用户可以完成两件事：

1. 看目标院校、专业和方向的官方招生变化，并回到官方来源。
2. 上传论文，提出问题，得到带页码和原文引用的答案。

你作为运营者只需要关心三个页面：

```text
首页             /                    用户看研究动态和招生变化
审核后台         /admin               你审核自动抓取到的候选
文献工作台       首页 → 文献工作台     用户上传论文、提问、查看证据
```

不需要每天理解 Git、Actions artifact、候选 JSON、WSGI 或数据库表。

## 1. 产品最终效果

### 1.1 用户首页

用户打开首页，可以看到：

- 最近已核验的招生变化
- 复试、保研、论文入门、AI 工具和院校信息
- 按大三、大四、研0筛选内容
- 搜索、收藏、未读状态
- 10 所目标院校的官方招生入口

每条招生变化都包含：

```text
学校 + 院系
专业代码 + 方向代码
变化内容
官方来源链接
核验时间
本科生怎么用
```

用户不需要看“候选 JSON”或“后台审核日志”，只看到审核后的结果。

### 1.2 文献工作台

用户可以：

- 上传自己的 PDF
- 直接使用 13 篇精选演示论文，不需要先上传
- 对整个文献库提问
- 让系统只从原文中找答案
- 看到每条结论对应的文档、页码和原文引用
- 直接打开 PDF 对应页
- 导出 Markdown 证据单
- 在 24 小时后自动清理临时上传文件

当前限制：

- 每个会话最多 10 篇
- 单文件不超过 8MB
- 每个会话最多 4000 个块
- 扫描版 PDF 没有 OCR，可能无法检索

### 1.3 审核后台

你打开 `/admin` 后可以看到：

- 待审核的新方向
- 待审核的变更方向
- 候选与正式库的字段差异
- 高风险字段
- 官方来源
- 通过和拒绝按钮
- 最近审核记录

你确认后，系统会：

- 新建正式招生记录，或
- 把新方向追加到已有招生文档，或
- 覆盖已经存在且你明确勾选“覆盖”的方向

通过后，首页会自动出现经过审核的招生变化。

## 2. 完整产品链路

```text
官方招生网站
      │
      │ 定时自动抓取
      ▼
候选数据 candidate
      │
      │ 自动与正式库比较、过滤
      ▼
审核队列 /admin
      │
      │ 人工核对官方来源和关键数字
      ▼
正式数据 programs + admission_records
      │
      ├── 首页信息流 /api/radar
      └── 招生变化事件 /api/changes
                    │
                    ▼
             首页“最近招生变化”

用户提问
      │
      ▼
文献工作台：检索 → 拒答 → 生成 → 页码引用
```

核心原则：

> 自动抓取可以发现变化，但高利害招生信息不能未经人工审核直接发布。

## 5. 你每天怎么工作

### 每天

1. 打开审核台：

```text
https://yulpio.pythonanywhere.com/admin
```

2. 输入管理员令牌登录。

3. 有候选就逐条审核；没有候选就关闭。

4. 对每个候选确认：

- 学校和院系是否正确
- 专业代码和方向代码是否正确
- 招生计划是否正确
- 推免人数是否正确
- 考试科目是否正确
- 官方来源是否可打开
- 内容是否适合目标用户

5. 选择：

- 核验通过并发布
- 拒绝，并填写原因

6. 如果通过的是新增方向或计划/科目变化，刷新首页检查“最近招生变化”。

### 每周

- 检查 GitHub Actions 是否连续成功
- 检查审核日志是否有误操作
- 抽查首页招生变化能否打开官方原文
- 检查是否有长期未处理候选

### 不需要每天做

- 不需要下载 artifact
- 不需要手动上传候选 JSON
- 不需要手工编辑正式 JSON
- 不需要理解 Git commit
- 不需要理解 WSGI

## 6. 首页、审核台、工作台分别是什么

### 首页

面向用户。只展示已经审核通过的内容。

### 审核台

面向你。只处理“新增、条件变化或需要修正”的候选。

未变化候选、重复候选、已拒绝候选和无关院系不会进入队列。

### 文献工作台

面向用户做论文阅读、复试材料、导师沟通和研究入门。

这三者通过“正式内容和官方来源”连接，不直接共享未审核候选。

## 7. 重要概念解释

### 候选 candidate

自动抓取器从官网提取出的“待审核数据”。它不是正式数据，也不会直接出现在首页。

### 正式数据

你审核通过后写入 `programs.json` 和 `admission_records.json` 的数据。

### 招生变化事件 change event

正式数据发生变化后生成的一条用户可读消息，例如：

```text
新增研究方向：085400 / 03 强军计划
```

### artifact

GitHub Actions 保存采集结果的归档文件，用于审计和兜底，不是用户页面。

### 审核队列

`/admin` 中等待你确认的候选集合。

### 用户可见变化

`user_visible=true` 的变化事件才会出现在首页。

纯招生说明措辞修正默认不进入公开信息流，避免制造无意义动态。

## 8. 数据和接口结构

### 数据文件

```text
data/schools.json              学校主表
data/sources.json              官方来源注册表
data/programs.json             正式专业和方向
data/admission_records.json    正式招生文档
data/radar_items.json          人工精选内容
data/change_events.json        已核验招生变化
data/candidates/               候选队列和审核运行时数据（不提交 Git）
```

### 主要公开接口

```text
GET /api/radar          首页信息流
GET /api/changes        首页最近招生变化
GET /api/schools        院校入口
GET /api/sources        采集源
GET /api/programs       正式专业方向
GET /api/admissions     正式招生文档
GET /api/docs           当前会话文献
POST /api/upload        上传 PDF
POST /api/ask           对文献提问
GET /api/file           打开原文 PDF
```

### 管理接口

```text
GET  /admin                      审核页
GET  /api/admin/status           配置状态
GET  /api/admin/pending          待审核队列
POST /api/admin/approve          审核通过
POST /api/admin/reject           拒绝候选
POST /api/admin/ingest           GitHub Actions 自动入库
```

## 10. 当前已知问题与下一步优化

### 优化 1：后台显示最近同步状态

现在队列为空时，需要额外确认 Actions 是否成功。

下一版后台应直接显示：

```text
最近同步：11月1日 20:26
清华：收到 2，入队 2
PKU：收到 1，未变化 1
```

### 优化 2：官方来源按钮

审核详情中应直接提供：

```text
打开官方原文 ↗
```

减少复制链接。

### 优化 3：高风险字段二次确认

计划数、推免人数、考试科目变化时，要求额外确认，不能与普通说明修改共用同一个按钮。

### 优化 4：审核历史筛选

按学校、专业、通过/拒绝和日期查看审核历史。

### 优化 5：连续运行验证

建议先连续运行 3～7 天，检查：

- 每日抓取成功
- 同期候选不重复入队
- 拒绝候选不会重复出现
- 审核后变化事件正确
- 首页来源链接可打开

## 12. 什么叫“自动化信息流完成”

满足以下条件后，才可以称为自动化信息流完成：

- 每日抓取连续稳定运行至少 7 天
- 无变化时审核队列为空
- 有变化时自动进入审核队列
- 审核通过后自动写入正式数据
- 首页自动出现已核验变化
- 每条变化能打开官方来源
- 错误和失败能在 Actions 或后台看到

当前已经完成主体，但还需要：

- 拉取最新部署代码
- 后台补最近同步状态
- 连续运行验证

## 13. 现在最应该做什么

不要继续增加学校、账户、支付或新功能。

按顺序：

```text
1. 确认线上运行的是最新提交
2. 审核当前队列中的真实候选
3. 补后台同步状态和官方来源按钮
4. 连续观察 3～7 天
5. 找 3～5 个真实本科生试用
6. 根据使用反馈决定下一阶段
```

判断产品是否有希望的指标：

- 用户是否点击“招生变化”
- 用户是否从变化进入文献工作台
- 用户是否上传第二篇论文
- 用户是否第二次回来
- 用户是否收藏目标院校或专业

代码写得更多，不等于产品更接近成功。
